# Outlook2iCloudCal 設計

## 目的

会社の Outlook カレンダーにある予定を、個人の iCloud カレンダーへ自動で写す macOS のメニューバー常駐アプリを作る。iCloud 側の予定を読むのは本人だけで、私用の iPhone や Mac から仕事の予定を確認できるようにすることが目的である。同期は Outlook から iCloud への片方向に限る。

Outlook の予定は `mcporter` 経由で `aws-outlook-mcp` から取得する。`aws-outlook-mcp` は `mwinit` で発行した証明書を必要とし、朝など証明書が切れている時間帯は取得に失敗する。この失敗は日常的に起きるものとして扱い、その回の同期を黙って見送る。

リポジトリは `rewse/outlook-to-icloud-calendar` として GitHub で公開する。アプリ名は `Outlook2iCloudCal` とする。

## ゴール

- 1 時間ごと（初期値。メニューから変更できる）に Outlook の予定を取得し、iCloud の専用カレンダー `Business` に差分を反映する。
- 証明書が切れていても、アプリは落ちず、エラーダイアログも出さない。メニューバーのアイコンで状態が分かる。
- 取得が途中で切れたときや、削除がまとめて起きたときに、iCloud 側の予定を誤って大量に消さない。
- 異常が起きたとき、原因をあとから調べられるログが常に残っている。

## ノンゴール

- iCloud から Outlook への書き戻しや、双方向の同期。
- メールや To Do の同期（カレンダーだけを扱う）。
- 予定の本文、出席者、主催者、リマインダーの同期。
- 他人の共有カレンダーや共有メールボックスの同期。
- Mac App Store での配布や公証（notarization）。

## アンチゴール

- 証明書切れや取得失敗をきっかけに `Business` の予定が消えること。取得に失敗した回は何も書き込まない。
- 公開リポジトリに実際の予定データ（件名、場所、会議 URL）が入ること。テストのフィクスチャは架空のデータで作る。
- 本人が手で `Business` 以外のカレンダーに入れた予定にアプリが触れること。

## 同期の仕様

### 取得範囲

取得した日を基準に、1 カ月前から 6 カ月後までを範囲とする。10/30 に取得するなら 9/30 から 4/30 までである。範囲の境界をまたぐ予定は範囲内として扱う。

範囲を月単位の 7 区間に分けて扱う。10/30 の例なら 9/30〜10/30、10/30〜11/30、…、3/30〜4/30 である。`calendar_view` は定期予定を回ごとに展開して返すので、繰り返しルールの解釈はいらない。

2026-10-30 に確かめた `calendar_view` の挙動は次のとおり。

- `view` は開始日を暦の区切りまで前に広げる。`view=month` に `03-30-2027` を渡すと 3/1 から返り、`view=week` は週の初めから返る。`view=day` が範囲を一番正確に扱う。
- `end_date` は `view` に関係なく効く。
- 7 カ月分（9/30〜4/30）を 1 回で取ると約 1,500 件が返り、件数の上限らしきものは見当たらなかった。
- 範囲より前に始まって範囲内まで続く予定（長期の終日予定など）も返る。

呼び出しを 1 回にするか区間ごとに分けるか、どの `view` を使うかは builder に任せる。どちらでも、返った予定は手元で 7 区間に振り分け、範囲外の予定は捨てる。

### 写す項目

開始日時、終了日時、件名、場所の 4 つだけを写す。本文、出席者、リマインダーは写さない。場所には会議 URL が入ることがあるが、そのまま写す。

### 写す予定の条件

既定は「写さない」で、次の条件をすべて満たす予定だけを写す。

- `response` が `Accept`（承諾済み）または `Organizer`（自分が主催。中身のない `Block` のような予定も含む）。
- `isCanceled` が false で、件名が `Canceled:` で始まらない。
- 件名が `Declined:` で始まらない。
- `isAllDay` が false。

`Decline`、`Tentative`、未返答、未知の値など、`response` がほかの値の予定はすべて写さない。ログには除外の理由を書き、未知の `response` の値はその値も書く。

### 書き込み先

iCloud アカウントに `Business` という専用カレンダーを置き、アプリはその中だけを読み書きする。Mac のカレンダーに登録済みの iCloud アカウントへ EventKit で書き込む。`Business` がなければ、初回の同期で iCloud のソースに作る。

### 差分同期

通常の同期では、範囲内について次の 3 種類の差分を反映する。

- 追加：Outlook にあり、`Business` にない予定。
- 更新：両方にあり、写す 4 項目のどれかが違う予定。
- 削除：`Business` でアプリが管理していて、今回の取得結果（除外後）にない予定。

Outlook 側で予定が消えたように見えるのは、日常的な操作の結果であることが多い。自分の予定を削除した、キャンセル通知を予定表から削除した、承諾をキャンセルや仮承諾に変えた、終日に変えた、範囲外へ動かした、といったケースである。削除は通常の操作として反映し、件数が異常なときだけ止める（後述）。

範囲より古くなった予定（1 カ月より前）は管理の対象外として放置し、消しも直しもしない。

### 予定の対応づけ

Outlook の `meetingId` は定期予定でも回ごとに異なるので、これを予定の識別子として使う。`Business` の各予定と `meetingId` の対応をどう持つか（EKEvent の `url` などに識別子を埋めるか、ローカルの対応表を持つか、その両方か）は builder に任せる。ただし、アプリが作っていない予定（本人が手で `Business` に入れた予定）を管理中と誤認して消さない作りにする。`meetingChangeKey` は更新の検出に使ってよい。

`Business` はアプリ専用のカレンダーとして扱う。通常の同期が消すのは管理中の予定だけで、手で入れた予定や対応が分からなくなった予定は残す。そうした予定は「初期化して再取得」で範囲内ごと片づく（設計上の判断）。

## 安全装置

### ゲート 1：取得の完全性

同期の前に、7 区間それぞれの取得件数を確かめる。件数は呼び出しの単位ではなく、手元で振り分けた区間ごとに、除外する前の生の件数で数える。1 回の呼び出しが途中で切れた場合も、後ろの区間が 0 件になるので検出できる。どれか 1 区間でも 0 件なら取得が途中で切れたとみなし、その回を丸ごと破棄する。1 カ月まるごと予定がゼロになることは運用上あり得ない。破棄した回は `Business` に何も書き込まず、区間ごとの件数をログに残す。メニューバーの表示は証明書切れと同じ扱いにする。

### ゲート 2：大量削除

差分を計算した結果、削除の件数が、範囲内で管理している予定の 10% 以上、かつ 5 件以上なら、削除だけを保留する。追加と更新はそのまま反映する。

保留は同期のたびに計算し直す。取得の一時的な不調が原因なら、次の同期で削除の候補が消えた時点で保留は自動的に解除される。本当に予定が消えたのなら保留が続き、本人がメニューの「削除を実行…」を押すまで削除しない。保留中は、次の自動同期でも削除しない。保留した削除を「破棄する」操作は置かない。破棄しても次の同期で同じ削除が再び出るからである。

### 証明書切れと取得失敗

`mcporter` の呼び出しが失敗した回は、何も書き込まずに見送る。原因が証明書切れだと判定できたときは、アイコンを赤い印付きにして、メニューの先頭に「証明書が切れています。mwinit してください」と出す。判定の方法（エラー出力の文言を見るか、Midway の Cookie の期限を見るか）は builder に任せる。証明書切れ以外の失敗はログに残し、アイコンは builder が適切と考える表示にする。

### 通知

証明書切れ以外の異常は、メニューバーの表示に加えて macOS の通知（`UserNotifications`）でも知らせる。対象はゲート 1 による破棄、ゲート 2 による削除の保留、証明書切れ以外の取得や書き込みの失敗である。証明書切れは朝に必ず起きるので通知しない。

同じ異常が続く間に毎回通知すると 1 時間ごとに鳴り続けるので、正常から異常へ、または異常の種類が変わったときだけ通知する。削除の保留は、保留の件数が増えたときにも通知する（設計上の判断）。通知の許可は初回起動時に求める。

`mcporter` の出力は、JSON の前後にデータ境界を示すマーカーが付いて返ってくることがあるので、JSON 配列だけを取り出して解析する。

### 初期化して再取得

メニューから手動で実行する。確認ダイアログを 1 回出したあと、範囲内の `Business` の予定を、アプリが管理しているかどうかに関係なく全部消してから Outlook の予定を取り直す。範囲より古い予定は消さない。取得に成功し、ゲート 1 を通過してから入れ替える順番にする。証明書切れのまま押しても、`Business` が空になることはない。大量削除のゲート 2 は通さない。

## メニューバー

アイコンは普段モノクロのテンプレート画像で、ライトモードとダークモードに追従する。異常時だけ色付きの印を付ける。証明書切れ（とゲート 1 による破棄）では赤い「!」、削除の保留中ではオレンジの「⏸」を付ける。

メニューの項目は上から次の順に並べる。

1. 異常時の案内（証明書切れ、または「削除 N 件を保留中（管理中 M 件の P%）」と「削除を実行…」）
2. 最終同期の時刻
3. 直前の同期件数（追加・更新・削除。保留があれば保留件数も）
4. 今すぐ同期
5. 自動同期の間隔（サブメニュー。15 分、30 分、1 時間、3 時間。初期値は 1 時間）
6. ログを Finder で表示
7. 初期化して再取得…
8. 終了

ブレインストーミングで使ったモックアップの内容は、この節がすべてである。

## ログ

`~/Library/Logs/Outlook2iCloudCal/` に、1 日 1 ファイルで書き出す。同期 1 回ごとに次の内容を残す。

- 区間ごとの取得件数（除外前）
- 除外した件数と、その理由ごとの内訳
- 追加、更新、削除、保留した予定それぞれの件名と日時
- ゲートの判定結果
- エラーの内容

ログには件名などの予定データが入るが、ローカルにしか置かないのでそのまま書く。14 日より古いログファイルは、アプリの起動時と、毎日最初の同期のときに削除する。

## 作り方

### 選んだ方式

Swift のネイティブアプリにして、iCloud への書き込みに EventKit を使う。

検討したのは次の 3 つである。

| 方式 | 長所 | 短所 |
|---|---|---|
| A. Swift＋SwiftUI `MenuBarExtra`＋EventKit | Apple 純正の API だけで iCloud を読み書きできる。パスワード管理がいらない。メニューの状態表示や確認ダイアログを自然に作れる | 初回にカレンダーへのアクセス許可がいる。署名を固定しないと、ビルドのたびに許可を求められる |
| B. Python＋rumps＋CalDAV | macOS の許可ダイアログが出ない | iCloud の App 用パスワードを発行して Keychain で管理する必要がある。iCloud の CalDAV 特有のクセがある。アプリ化に py2app などの手間がかかる |
| C. スクリプト＋launchd＋SwiftBar | 一番手軽 | 間隔の変更や削除の承認をファイル経由でやり取りすることになる。SwiftBar のインストールが別途必要 |

本人が A を選んだ。AppleScript でカレンダー.app を操作する案は、数百件規模の突き合わせを毎時行うには遅く壊れやすいので、候補から外した。

### ビルド環境

`/Applications/Xcode.app`（Xcode 27.1）が入っているが、`xcode-select` は Command Line Tools を向いている。`xcode-select` は他のプロジェクトにも影響するので変更しない。ビルドスクリプトの中で `DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer` を指定し、Xcode の SDK とマクロプラグインを使う。Command Line Tools 付属の macOS 27 SDK では SwiftUI の `@State` がマクロになっており、そのプラグインが Xcode にしか入っていないからである。

プロジェクトの形式（SwiftPM と `.app` を組み立てるスクリプトにするか、Xcode プロジェクトにするか）は builder に任せる。`~/git/MeetNote` の `build.sh` が SwiftPM から `.app` を組み立てる先行例になる。

### 署名と常駐

カレンダーへのアクセス許可は署名にひも付くので、アドホック署名ではなく、このアプリ専用の自己署名のコード署名証明書で署名する。証明書がなければ作るスクリプトを用意する。ログイン時の自動起動は `SMAppService.mainApp` で登録する。インストール先とインストール手順は builder に任せる。

### mcporter の呼び出し

GUI アプリはログインシェルの PATH を引き継がないので、`mcporter` は `/opt/homebrew/bin/mcporter` のように絶対パスで呼ぶか、PATH を明示して呼ぶ。`mcporter` の設定は `~/.mcporter/mcporter.json` にあり、サーバー名は `aws-outlook-mcp`、使うツールは `calendar_view`（引数 `view`、`start_date`、`end_date`、日付は `MM-DD-YYYY`）である。範囲の扱いは「取得範囲」の節に書いた。

### リポジトリの設定

コードには `aws-outlook-mcp`、`mwinit`、`calendar_view` のフィールド名、証明書切れのエラー文言をそのまま書いてよい。README は英語で書き、社内ツールの名前は出さずに一般化する（たとえば「MCP 経由で Outlook カレンダーを返すサーバー」「認証用の証明書を更新するコマンド」）。

アプリは 1 台の Mac でだけ動かす。複数台からの同時書き込みや、その重複排除は考えない。iCloud にはまだ `Business` カレンダーがないので、既存の予定の取り込みや移行の手順はいらない。

公開リポジトリなので、`~/git/AGENTS.md` の GitHub 設定の方針（dependabot、gitleaks、trufflehog、pre-commit、SHA 固定など）に従う。Swift の lint を pre-commit に入れるかは builder に任せる。テストは EventKit と `mcporter` を差し替えられる作りにして、実際の iCloud と Outlook には触れない。

## builder に任せること

- `meetingId` と `Business` の予定の対応づけの持ち方
- 証明書切れの判定方法
- プロジェクトの形式、インストール手順、自己署名証明書の作成手順
- 起動直後やスリープ復帰後に同期が遅れていたとき、すぐ同期するかどうか
- 同期中の表示（アイコンのアニメーションなど）と、二重実行の防止
- Swift の lint とテストの構成
